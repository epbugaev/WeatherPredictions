# CLAUDE.md

Инструкции для ИИ-агентов, работающих с этим репозиторием.
Проект: ML для прогнозирования погоды на PyTorch (Python 3.10+, numpy, torch).

---

## 1. Принципы написания кода

- **Говорящие имена.** Переменные и функции называются по смыслу: `compute_geopotential_loss`, а не `f1`; `lead_time_hours`, а не `lt`. Однобуквенные имена допустимы только в формулах (`i`, `j`, `x`, `y`) и итераторах.
- **Одна функция — одна ответственность.** Если в названии появляется `and` или функция > ~50 строк без чёткой причины — дроби.
- **Плоская структура.** Максимум 3 уровня вложенности (`if/for/with`). Глубже — выносить в отдельную функцию или использовать ранний `return`/`continue`.
- **DRY.** Если одинаковый блок (≥ ~5 строк или нетривиальная логика) встречается дважды — выноси в функцию. Дублирование тензорных преобразований чаще всего значит, что нужен helper в [utils/](utils/).
- **SOLID:**
  - *SRP:* модель ≠ обучающий цикл ≠ загрузка данных. Не смешивай слои в [Models/](Models/), [train/](train/), [utils/](utils/).
  - *OCP:* новые модели/лоссы добавляются как новые классы/файлы, не правкой существующих веток `if model_name == ...`.
  - *LSP:* `nn.Module`-подклассы соблюдают сигнатуру `forward` своего семейства (например, видео-предикторы: `(B, T, C, H, W) -> (B, T, C, H, W)`).
  - *ISP:* не передавай в функцию весь `config`, если ей нужны 2 поля — передавай поля.
  - *DIP:* модель, лосс, оптимизатор, даталоадер передаются параметрами в `train_*`. Никакого `from configs.foo import LR` внутри логики обучения — конфиг читается на верхнем уровне ([train.py](train.py)) и пробрасывается явно.

## 2. Запрещённые конструкции

- **Никаких `try/except`.** Используй LBYL: проверяй `if path.exists()`, `if key in d`, `if tensor.numel() > 0` до операции. Если действительно нужен `try` (загрузка чекпоинта, парсинг внешнего файла, опциональная зависимость) — **сначала обсуди с пользователем**, потом добавляй.
- **Никаких локальных `import`** внутри функций/методов/классов. Все импорты — в начале файла, сгруппированы (stdlib → сторонние → локальные). Циклический импорт — повод реорганизовать модули (вынести общие типы/утилиты), а не маскировать его отложенным импортом.
- **Никакого мёртвого кода.** Удаляй сразу:
  - закомментированные блоки кода (история есть в git),
  - неиспользуемые `import`,
  - неиспользуемые параметры функций,
  - переменные, которым присвоено значение и которые больше не читаются,
  - забытые `print(...)`, отладочные `breakpoint()`, `pdb`-вызовы.

## 3. Оптимизация

- **Векторизация.** На тензорах/массивах — `torch`/`numpy` операции, а не `for`-циклы по элементам. Циклы допустимы по батчу/эпохам/шагам обучения и по разнородным операциям, не сводимым к broadcast.
- **Не пересчитывай.** Если величина (например, координатные сетки, маски, нормировочные статистики) одна и та же на всех шагах — считай один раз в `__init__` или вне цикла, сохраняй как буфер (`self.register_buffer`).
- **Не плоди копии.** Избегай `.clone()`, `.copy()`, `np.array(x)` поверх уже-тензора, `list(...)` поверх итерируемого — без явной причины (нужен writable view, отвязка от графа и т.п.). Для отвязки от autograd — `.detach()`, а не `.clone().detach()` без необходимости.
- **Структуры данных по назначению.** `set` для проверки членства, `dict` для lookup по ключу, `collections.deque` для FIFO. Не используй `list` там, где O(n) поиск становится узким местом.
- **GPU-специфика.** `.to(device)` — один раз, в начале; не двигай тензоры туда-сюда в горячем цикле. `torch.no_grad()` / `inference_mode()` в валидации и инференсе обязательны.

## 4. Документация

- **Docstrings.** Каждая публичная функция, класс и модуль имеет docstring в **Google-стиле**. Выбран один стиль на весь проект — не смешивай с NumPy/Sphinx.
- **Содержимое docstring:** краткое назначение (1 строка), `Args:` с типами и shape для тензоров (например, `x: torch.Tensor of shape (B, T, C, H, W)`), `Returns:` с типом и shape, `Raises:` (если применимо в LBYL-логике через `assert`/проверки), побочные эффекты (запись на диск, мутация аргументов, `wandb.log` и т.п.).
- **Type hints** обязательны на аргументах и возвращаемом значении публичных функций. Внутренние helper'ы — желательны. Используй `|` (PEP 604), `list[...]`, `dict[...]` — Python 3.10+.
- **Синхронизация документации.** При изменении сигнатуры/поведения публичного API обнови docstring и, если он описывает это поведение, [README.md](README.md).
- **CHANGELOG.md.** Веди в формате [Keep a Changelog](https://keepachangelog.com): секции `Added` / `Changed` / `Fixed` / `Removed` под `## [Unreleased]`. Записывай туда содержательные изменения (новая модель, изменение интерфейса конфига, удаление модуля), а не каждый коммит-опечатку.

## 5. Чистота репозитория

- **Не коммить:** временные файлы, локальные логи запусков, веса чекпоинтов, отладочные скрипты, `*.ipynb_checkpoints`, `__pycache__`, артефакты wandb/tensorboard. Если нужно — добавь в `.gitignore`.
- **Структура директорий:**
  - [Models/](Models/) — `nn.Module`-определения архитектур;
  - [training_strategies/](training_strategies/) — per-batch train/val стратегии (`StepStrategy`);
  - [trainer.py](trainer.py) — общий цикл обучения (DDP/AMP/scheduler/checkpoint/early-stop);
  - [train/](train/) — обучающие скрипты для конкретных моделей;
  - [utils/](utils/) — даталоадеры, лоссы, метрики, общие утилиты;
  - [configs/](configs/) — конфиги экспериментов;
  - [sh_files/](sh_files/) — shell-скрипты запуска;
  - [Research/](Research/) — экспериментальные ноутбуки/наброски.

  Не создавай новые директории верхнего уровня без явной необходимости — сначала проверь, не подходит ли существующая.
- **Перед завершением задачи** прогони чек:
  - неиспользуемые импорты (`ruff check --select F401`),
  - неиспользуемые переменные (`ruff check --select F841`),
  - забытые `print`/`breakpoint` (`ruff check --select T201,T100`),
  - закомментированный код.

## 6. Процесс работы

- **Сначала ищи, потом пиши.** Перед реализацией функции — `grep`/поиск по [utils/](utils/), [Models/](Models/): возможно, она уже есть (типичные кандидаты: загрузка ERA5, нормализация, метрики RMSE/ACC, geopotential-конвертация). Переиспользуй вместо дублирования.
- **Линтер и форматтер.** После изменений запускай `ruff check .` и `ruff format .`. Все предупреждения — устраняй, а не подавляй (`# noqa` только с явной причиной в комментарии и подтверждением пользователя).
- **Окружение.** Если нужно поставить пакет — предпочитай `uv pip install` поверх голого `pip`. Версии фиксируй в `requirements.txt` / `environment.yml`.
- **Git-коммиты** — на английском, conventional commits (`feat:`, `fix:`, `refactor:`, `docs:`, `chore:`).
- **Конфликт с этим файлом.** Если правило отсюда мешает выполнить задачу корректно — **не нарушай молча**. Явно подними вопрос с пользователем: какое правило, почему мешает, какой предлагается обход. Решение фиксируется в этом файле или в CHANGELOG.
